### 2026-05-01 — Critical: error envelope unwrap + global mutation error handler
**Change:** Two related must-fix items uncovered by error-handling audit during PR #25 device review:
1. **`src/lib/api.ts` — error envelope unwrap.** Backend serialises errors as `{ error: { code, message, statusCode, field? } }` (per `src/api/app.ts setErrorHandler` calling `AppError.toJSON()`), but the rebaseline client read `json.code` / `json.message` from the top level — so every backend error reached `mapError()` as `code='UNKNOWN'`, producing the universal "Something went wrong. Please try again." Salvaged the unwrap from cefaf45 (it existed there but was missed in the rebaseline salvage list): if `json.error` is a non-array object, read `code` / `message` / `field` from there, otherwise fall back to top-level for backwards compatibility. With this fix, every existing mapping in `lib/errors.ts` and every screen-level handler (LoginScreen formError, RegisterScreen branded cards for EMAIL_ALREADY_EXISTS / PHONE_ALREADY_EXISTS, usePhoneVerify inline OTP errors, ResetPassword token-expired full-page state, etc.) starts working correctly.
2. **`app/_layout.tsx` — global MutationCache.onError.** PC1/PC2/PC3 profile-completion screens used a `try { await update.mutateAsync(...) } catch { /* toast handled by global error boundary */ }` pattern, but no global handler actually existed — failures were silent. Added `MutationCache({ onError })` on the QueryClient that calls `emitToast(mapError(error).message, 'danger')`. Co-located the imperative `emitToast()` handle in `Toast.tsx` (registered by `ToastProvider` on mount), mirroring the existing `api.onSessionExpired(cb)` pattern. No double-display risk: login / register / forgot / reset / verify-email / verify-phone use direct `authApi.X()` calls (not useMutation), so the global handler doesn't fire for their errors. The three useMutation call sites in scope (useUpdateProfile, useUpdateAvatar, useUpdateInterests) had no local onError, so the global handler is purely additive.
**Reason:** Owner reported on device that login with a non-registered email surfaced "Something went wrong" — generic and unhelpful. Audit traced root cause to (1) the unwrap miss in lib/api.ts. (2) was the secondary silent-failure issue on PC saves. Both are critical for PR #25 — the entire error-handling infrastructure (lib/errors.ts mappings, screen-level surfacing) is correctly wired, it just couldn't see the codes. Files: `src/lib/api.ts`, `src/design-system/motion/Toast.tsx`, `app/_layout.tsx`, `tests/app/root-layout.test.tsx` (mock added for `MutationCache` and `emitToast`). 214/215 tests passing (same baseline). No new mappings added — deferred follow-up items (CURRENT_PASSWORD_INCORRECT for change-password, INVALID_INTERESTS for PC3, dead-branch cleanup for RESET_TOKEN_INVALID etc.) explicitly out of PR #25 scope.

### 2026-05-01 — Tier 1 keyboard-insets audit fix: focus-into-view on iOS for tall onboarding forms
**Change:** Audit of all 13 customer-entry-flow screens (Welcome → SubscribePrompt) found that only `RegisterScreen` correctly handled iOS focus-into-view. RegisterScreen relies on `automaticallyAdjustKeyboardInsets={Platform.OS === 'ios'}` on its ScrollView (iOS 13+ native API) and has **no** `KeyboardAvoidingView` wrapping. Other screens used `KAV behavior="padding"` alone, which lifts content but doesn't actively scroll an off-screen focused field into view. Fixed in PR #25 by aligning to RegisterScreen's pattern in:
1. `src/design-system/components/ScreenContainer.tsx` — added aaki on the ScrollView body when `scroll` prop is true; neutralised KAV `behavior` to `undefined` on iOS so KAV doesn't double-compensate with aaki. Covers `ResetPasswordScreen` and any other consumer.
2. `src/features/profile-completion/screens/PC1AboutScreen.tsx` — added aaki, neutralised KAV behavior on iOS.
3. `src/features/profile-completion/screens/PC2AddressScreen.tsx` — added aaki, neutralised KAV behavior on iOS.
Tier 2 (short single-screen forms — Login, ForgotPassword) deliberately untouched; KAV alone is sufficient when the form fits above the keyboard. `VerifyPhoneScreen` deliberately untouched: its main form is a fixed-layout `<View>` (no ScrollView), correct for the short OTP layout; the country-picker FlatList lives inside the BottomSheet which has its own keyboard handling. Android relies on `softwareKeyboardLayoutMode: 'pan'` already set in `app.config.ts`, pending native rebuild (tracked separately).
**Reason:** On-device QA surfaced the standard question "does a focused field scroll into view above the keyboard". The correct iOS pattern is aaki-only — KAV `behavior="padding"` + aaki double-compensates, lifting content twice and producing a visibly-broken layout (huge blank space between the bottom of the form and the top of the keyboard, equal to keyboard height). Caught and corrected on-device during PR #25 device review. Files: `ScreenContainer.tsx`, `PC1AboutScreen.tsx`, `PC2AddressScreen.tsx`. No behavioural change for users on screens not in the Tier 1 list.

### 2026-05-01 — On-device QA fixes: register password trap, sheet keyboard gap, empty-blur errors, postcode area label
**Change:** Four on-device QA findings against PR #25 fixed:
1. **Register password trap.** `RegisterScreen.tsx` had a `useEffect` that re-focused the first invalid field on every `fieldErrors` change. Combined with the password's `onBlur` validator (which sets a field error itself), tapping into password and blurring to another field re-focused password — the user could not move on. Removed the effect; focus is now applied at submit time only, with API field errors surfaced via a refactored `useRegisterFlow.submit()` that returns `Record<string, FieldError> | null` so the screen can `focusFirstInvalid` after the API rejects.
2. **BottomSheet keyboard corner gap.** Sheet was anchored at `bottom: keyboardHeight`, leaving iOS's keyboard rounded-corner gaps to leak the dark scrim. Re-anchored to `bottom: 0` with `paddingBottom: keyboardHeight + spacing[5]` so the white surface extends behind the keyboard.
3. **onBlur empty-field errors.** `RegisterScreen` password and phone `onBlur` validators surfaced "must include uppercase…" / "too short" errors for empty fields, so tapping in/out of an empty field marked it errored even before any submit attempt. Validators now no-op on empty input and clear any existing field error; required-field enforcement happens only at submit.
4. **Postcode area label.** `PC2AddressScreen.tsx` postcode lookup originally displayed `admin_district` from postcodes.io — for HD1 4RU that returned "Kirklees" (the metropolitan borough council). The right field varies by region, so `pickAreaLabel()` picks the most user-recognisable place name: (i) civil `parish` when it's a real name (rural villages — CO7 0UB → "Brightlingsea"); (ii) `admin_ward` when the postcode is in London (NW2 7UD → "Dollis Hill", SW1A 1AA → "St James's") because London is almost entirely unparished and constituency names are politically broad ("Brent East", "Cities of London and Westminster"); (iii) `parliamentary_constituency` for other urban postcodes (HD1 4RU → "Huddersfield"); (iv) `admin_district`, then `admin_ward` as final fallbacks. Postcodes.io's "<district>, unparished area" placeholder is detected and skipped. Display-only — only the raw postcode is sent to the backend, so no contract change.
**Reason:** All four are on-device QA findings during PR #25 device review (2026-05-01). None are backend or contract changes — pure client UX corrections. Files: `RegisterScreen.tsx`, `useRegisterFlow.ts`, `BottomSheet.tsx`, `PC2AddressScreen.tsx`. `customer-flow-current.md` §5.2 (PC2) unchanged at the spec level — postcode display field was not previously documented; current behaviour now matches user expectation.
