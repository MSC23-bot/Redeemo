- **Set-equality tally.** Every blueprint module M1 to M24 now has exactly one row with a target screen and a wave (M23 Feature flags / config, previously implicit in Operational Status, is now an explicit row -> W3 §3.4 with a config-health slice in W1 §1.10). - **Relocation of existing capability.** The ~15 admin capability areas and merchant-facing surfaces that exist on disk (`approval:read/action/apply-edit`, `merchant:read/create-draft/suspend`, `branch:confirm-location`, editApplier/voucherApprover/branchLifecycleApplier, the admin bell, Operational-Status signals, per-merchant AuditLog + CommunicationLog timelines, Merchant Insights foundation) each map to a Wave 1/2/3 target screen above; none is dropped in the re-home.
- **Reserved emitters / dead-ended intakes each get an outlet.** `ADMIN_REVIEW_ASSIGNED` (reserved, unemitted) -> the future Tasks assign/reassign flow (M8, W2 §2.3) with governance visibility in Global Audit (M21, W1 §1.8); delivery/bounce notification states -> Operational Status (M22, W1 §1.10) + Communications delivery monitor (M7, W2 §2.2); suggested tags (M13), fraud telemetry + reversibility (M11), MERCHANT_PROFILE_EDIT into the unified queue (M2), CmsContent/RmvTemplate (M18) each land in a wave, satisfying "every intake has an outlet".
- **Authority/safety boundaries carried through:** act-FOR-not-AS + reason/audit on every on-behalf action; single-actor approval today (four-eyes future; the blueprint §7 "FOUR-EYES" column = the merchant submit-then-approve staging, still single-admin-actor on the Redeemo side); PII gating + no customer-home map; PIN never shown; no admin-signs; DPIA-gated analytics; purpose-scoped export.
